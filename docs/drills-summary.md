## 三、单点分析

按"停掉之后用户还能不能用"排序：

| 组件 | 副本数 | 有无持久化 | 停掉之后 |
|---|---|---|---|
| Redis | 1 | 无 | **业务直接不可用**，3 秒内出现 500，恢复 6 秒，数据丢失 |
| API | 2 | 无状态 | 删一个无感，全删则 100% 不可用 |
| Prometheus | 1 | 无 | 观测直接归零，告警体系失效；恢复后历史指标清空 |
| Grafana | 1 | 配置在 ConfigMap | 面板不可用，但采集继续 |
| 节点 | 1 | — | 全部同时不可用 |
| 镜像源 | 外部依赖 | — | 重建时卡在拉取阶段（11-18 实证） |

**结论：真正的单点是 Redis 和那个唯一的节点。** API 的双副本只解决了"单个 Pod 挂掉"，解决不了"Redis 挂掉"和"节点挂掉"。

下次出故障，最可能的入口是 Redis 相关的操作（重启、扩容、配置变更），因为它既单副本又没有持久化。

## 五、三个方法论结论

**一，观测方法本身要验证。** 删 Pod 那场第一次用 `kubectl port-forward` 探测，报告了 39 次失败；
换成集群内探针是 0 次。同一次操作、两种测法、相反结论。原因是 port-forward 的隧道固定在被删的
Pod 上，Pod 一死隧道就断。**测故障之前先问：我的观测工具会不会被这次故障波及。**

**二，告警要覆盖"没有数据"。** 比例类规则在空向量上不触发，导致最严重的故障最安静。
`absent()` 是补这个洞的标准工具。

**三，一次只改一个变量。** 这轮每次改动都单独提交、单独复测，所以 211→89 秒这个数字能归因到
具体参数，而不是"改了一堆东西之后变好了"。

## 六、可写进简历的表述

> 在本地单节点 Kubernetes（Docker Desktop/WSL2）上交付 FastAPI + Redis 服务，双副本 API 加就绪探针；
> 完成三次故障演练：依赖故障下用户 3 秒受影响、告警发现耗时经规则调优从 211 秒降至 89 秒、
> 单 Pod 删除用户零失败且 2 秒自愈、整体断流经补 `absent()` 规则后从无告警变为 110 秒内告警。
> 所有数字来自集群内探针与 Prometheus 规则状态，样本量与计时口径见仓库 `docs/drills-summary.md`。

**必须同时说出**：单节点、非高可用、Redis 单副本无持久化、告警无通知渠道。
