# 范围与边界

这份文档说明项目做了什么、明确不做什么、以及为什么。面试里"你没做什么、理由是什么"比"你做了什么"更能说明判断力，所以这一页不省略。

## 一句话定位

这是一个**单节点本地 Kubernetes 上的交付与可观测演练项目**，用来验证"部署、观测、告警、故障处置"这条链是否能跑通并被测量。它不是生产系统，也不是云上部署。

## 做什么

| 方面 | 内容 |
|---|---|
| 被运维对象 | FastAPI 待办 API（双副本）+ Redis（单副本） |
| 交付方式 | 声明式清单 + `scripts/bootstrap.ps1` 一键重建 |
| 镜像 | GitHub Actions 构建，按提交哈希打 tag，推到 GHCR |
| 观测 | Prometheus 按 Pod 发现抓取，黑盒探测器每 5 秒探测业务路径，Grafana 七块面板，四条告警规则 |
| SLO | 可用性 99%、95% 请求在 100ms 内，1 小时滚动窗口，Wilson 置信区间判定 |
| 演练 | 依赖故障、单 Pod 删除、整体断流三场，全部带计时 |
| 证据 | `evidence/` 下按时间归档的原始输出 |

## 不做什么，以及原因

| 不做 | 原因 |
|---|---|
| 三节点集群与节点级容灾 | 预算内做不到真实验证，写了就是宣称没测过的东西 |
| 反亲和、PodDisruptionBudget | 单节点上没有意义，反亲和无处调度 |
| TLS、域名、Ingress | 演示没有外部用户，加了只增加复杂度；本地访问用端口转发 |
| 多环境（dev/prod） | 一份环境已经够暴露问题，多环境会稀释精力 |
| ArgoCD / 服务网格 | 与"测量与复盘"这个目标无关，属于另一个题目 |
| Alertmanager 与真实通知 | 没有真实接收方，配了只能证明配置写对，证明不了值班流程 |
| 高并发压测 | 500m CPU 限制下测出来的是限流值，不是服务能力，写进简历会误导 |
| 云上部署（ECS/ACK） | 已明确裁决不做；早期文档里"云上"的表述已全部改写为本地 |

## 环境与成本

- 运行在本地 Docker Desktop 的 Kubernetes（WSL2，单节点，v1.36.1）
- 云资源开销为 0；唯一的成本是本机资源占用
- 镜像从 GHCR 与 Docker Hub 拉取；**Docker Hub 直连被网络阻断时必须走镜像加速器**，否则重建会卡在拉取阶段（2026-11-18 实测）

## 数据与隐私

- 仓库里没有真实密钥、token、kubeconfig、SSH 私钥、公网 IP 或域名
- 证据文件里出现的地址都是 RFC1918 私网地址（10.244.x、10.96.x、172.20.x）
- 演示数据（待办条目）不含个人信息

## 可复现的边界

别人克隆仓库后能复现的部分：

- 清单能否应用、Pod 能否起来、面板与告警是否生效、脚本是否可用

不能完全复现的部分：

- **具体耗时数字**（重建 7.8 秒、MTTD 89 秒）依赖本机性能、镜像是否已缓存、镜像源速度
- **Docker Desktop 的可用性**：它不运行时所有命令都会失败，这不是项目缺陷
- 网络环境：镜像源不通时会在拉取阶段失败

所以文档里给出的耗时都带了口径说明，不承诺"任何人任何机器都能得到同样数字"。

## 与"生产可用"的距离

如果要把这套东西变成生产可用的系统，至少还差：

1. Redis 改成带持久化的集群或多副本方案，并做故障切换测试
2. 节点从 1 个增加到 3 个，加反亲和与 PDB，并做节点故障演练
3. 告警接入通知渠道，测"人收到消息"的延迟，而不只是"规则变红"
4. 加黑盒探测，把发现耗时从分钟级压到秒级
5. 加认证与限流，配置 TLS

这些都不在本项目范围内，写在这里是为了说清楚边界在哪，而不是暗示"只差一点点"。
