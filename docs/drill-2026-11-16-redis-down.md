# 演练记录：Redis 依赖故障（2026-11-16）

## 目的

验证一件事：**当被依赖的 Redis 挂掉时，用户多快受影响，告警多快能发现，恢复后多快解除。**

这也是第一次给告警计时。之前的演练只有"firing / inactive"的定性记录，没有秒数。

## 场景与操作

- 场景：依赖故障。API 本身健康，但 Redis 不可用。
- 注入：`kubectl scale deployment/redis -n cloudp1 --replicas=0`
- 恢复：`kubectl scale deployment/redis -n cloudp1 --replicas=1`
- 探测：每 3 秒一次 `GET /todos`，非 200 记为受影响
- 告警状态：读 Prometheus 的 `/api/v1/rules?type=alert`
- 环境：本地单节点 Docker Desktop，2 个 API 副本

## 时间线

| 时刻 | 事件 |
|---|---|
| 15:10:55 | 注入开始（Redis 副本数改为 0） |
| 15:10:59 | 用户受影响，`GET /todos` 返回 500 |
| 15:12:43 | `TodoApiHigh5xxRate` 进入 pending |
| 15:14:30 | `TodoApiHigh5xxRate` 进入 firing |
| 15:14:51 | 恢复操作（Redis 副本数改回 1） |
| 15:14:58 | 业务恢复，`GET /todos` 返回 200 |
| 15:19:56 | 告警解除，全部规则回到 inactive |

## 关键数字

| 指标 | 数值 | 含义 |
|---|---|---|
| 注入 → 用户受影响 | 3.3 秒 | 故障传导到用户几乎是瞬时的 |
| 用户受影响 → 告警 firing | **211.2 秒（约 3.5 分钟）** | 发现耗时，比影响时长慢 64 倍 |
| 恢复操作 → 业务恢复 | 6.1 秒 | 恢复很快 |
| 恢复操作 → 告警解除 | 304.6 秒（约 5 分钟） | 告警"解除"比业务恢复慢 50 倍 |

证据：`evidence/2026-11-16-1519-drill-redis-down/`

## 最重要的发现：抓取可用率告警完全没有反应

`TodoApiScrapeAvailabilityLow` 全程停留在 inactive。

原因不是配置错，而是架构决定的：**Prometheus 现在按 Pod 发现并直接抓取 Pod IP，不经过 Service，也不依赖 Redis。**
Redis 挂掉不影响 `/metrics`，所以 `up` 一直是 1。

这条告警只能发现"采集本身断了"，无法发现"业务挂了"。它原来的设计意图写在 `docs/phase-observability.md` 里：
`up` 衡量的是采集可达性，不等于用户可用性。**现在有实测证据支撑这句话了。**

## 发现耗时为什么是 211 秒

按时间常数逐项拆：

- `TodoApiHigh5xxRate` 用 `rate(...[5m])`，需要至少两个抓取样本才有非零速率
- 规则 `for: 2m`，进入 pending 后要再等 2 分钟才 firing
- 抓取间隔 15 秒，所以"发现异常"本身就有 15 到 30 秒的滞后

三者相加就是三分钟以上。**这是规则参数决定的，不是偶然。** 想缩短只能改参数或换探测方式。

## 恢复耗时为什么是 304 秒

告警恢复的条件是表达式不再成立。5xx 比例的分子分母都在 5 分钟窗口里，业务恢复后旧样本还在窗口内，
要等它们滚出去，比例才会降到阈值以下。**业务恢复 6 秒，告警解除 5 分钟，这个差值对值班体验影响很大**：
故障已经恢复，告警还在响，人会被拉回去重新看一遍。

## 改进项

| 编号 | 改进 | 预期效果 | 验收方式 |
|---|---|---|---|
| 1 | 5xx 告警窗口从 `[5m]` 缩到 `[1m]`，`for` 从 `2m` 改 `1m` | MTTD 从 211 秒降到 1 分钟左右 | 重跑同一演练，对比数字 |
| 2 | 增加黑盒探测：定时打 `GET /todos`，失败即告警 | 不再依赖指标推断，直接测用户路径 | 同上 |
| 3 | 恢复判定与 firing 判定分开：恢复用短窗口，触发用长窗口 | 减少"业务已好、告警还响" | 观察恢复耗时 |
| 4 | 明确记录哪条告警负责哪类故障 | 避免下次又期待采集告警发现依赖故障 | 写进告警说明 |

## 一次演练得出的判断

- 当前配置能给"故障发生过"提供证据，但**给不了"及时知道"**。3.5 分钟的发现延迟，对演示够用，对值班不够。
- 采集可用率和业务可用性是两条不同的线，这次演练把它们的边界测出来了。
- 恢复路径比发现路径好得多：6 秒恢复，说明部署和依赖启动本身没问题，问题在检测。

## 还没做的

- 改进项 1 到 3 都还没实施，需要改 `k8s/prometheus.yaml` 的规则与抓取参数，再重跑一次对比。
- 只做了依赖故障一种场景，Pod 删除、采集中断两类还没测。
- 告警通知渠道（Alertmanager）仍然没有，所以"发现"目前等于"有人打开 Prometheus 或 Grafana 看"。

## 第二轮：改进后复测（2026-11-18）

### 改了什么

| 改动 | 改前 | 改后 |
|---|---|---|
| 规则评估间隔 | 默认 60 秒 | 15 秒 |
| 5xx 统计窗口 | `[5m]` | `[1m]` |
| 持续时间要求 | `for: 2m` | `for: 1m` |
| 请求量下限 | 无 | `rate > 0.1/秒`，避免单个请求就触发 |

### 预测与结果

改动前先写下预测：**MTTD 应落在 75 到 105 秒**，理由是三个环节相加：

- 请求变 5xx 到下一次抓取：0 到 15 秒
- 抓到后到下一次规则评估：0 到 15 秒
- `for: 1m`：60 秒

实测 **88.9 秒**，落在预测区间内。

### 两轮对比

| 指标 | 第一轮 11-16 | 第二轮 11-18 | 变化 |
|---|---|---|---|
| 注入 → 用户受影响 | 3.3 秒 | 3.2 秒 | 基本不变，故障传导路径没动 |
| 用户受影响 → firing（MTTD） | 211.2 秒 | **88.9 秒** | 快 2.4 倍 |
| 恢复操作 → 业务恢复 | 6.1 秒 | 6.2 秒 | 基本不变 |
| 恢复操作 → 告警解除 | 304.6 秒 | **63.4 秒** | 快 4.8 倍 |

证据：`evidence/2026-11-18-0923-drill-redis-down/`

### 结论

1. **缩短统计窗口同时改善了发现和解除。** 两者都依赖窗口：触发要看窗口内比例，解除要等旧样本滚出窗口。
   一处参数改动，两头收益。
2. **代价是更容易误报。** 1 分钟窗口里出现 1 次失败，比例就是 100%。所以加了请求量下限
   `rate > 0.1/秒`，低于这个量不判告警——低流量下的比例没有统计意义。
3. **没有解决的部分**：依赖故障时 `TodoApiScrapeAvailabilityLow` 仍然不会响，因为它看的是抓取可达性；
   现在最快能发现依赖故障的仍然是 5xx 规则，88.9 秒这个数字就是当前架构的下限。

### 待办

- 黑盒探测（定时打 `GET /todos`）才能把 MTTD 压到秒级，属于新增组件，未做。
- 告警没有通知渠道，88.9 秒只是"规则变红"的时间，不是"人知道"的时间。真实值班还要加上通知延迟。

## 第三轮：接入黑盒探测后（2026-11-18 13:44）

### 改了什么

新增 `blackbox-exporter`，每 5 秒直接请求业务路径 `GET http://todo-api:8000/todos`，只认 200 为成功。
对应告警 `TodoApiBlackboxProbeFailing`（`probe_success == 0`，`for: 30s`）。

它解决的是前两轮的根本问题：5xx 规则只能发现"应用还在响应、但返回错误"，
而 Redis 挂掉时应用可能连请求都处理不了，5xx 指标本身就没有新样本。

### 结果

| 指标 | 第一轮 | 第二轮（调窗口） | 第三轮（黑盒） |
|---|---|---|---|
| 注入 → 用户受影响 | 3.3 秒 | 3.2 秒 | 3.4 秒 |
| **用户受影响 → firing** | 211.2 秒 | 88.9 秒 | **37 秒** |
| 触发规则 | 5xx | 5xx | 黑盒探测 |
| 恢复 → 业务恢复 | 6.1 秒 | 6.2 秒 | 6.3 秒 |
| 恢复 → 告警解除 | 304.6 秒 | 63.4 秒 | 76 秒 |

预测 35 到 50 秒，实测 37 秒，落在区间内。

### 为什么快

| 环节 | 第一轮 | 第三轮 |
|---|---|---|
| 异常可见的延迟 | 抓取间隔 15 秒 + 窗口 5 分钟 | 探测间隔 5 秒 |
| 确认持续时间 | `for: 2m` | `for: 30s` |
| 规则评估 | 60 秒 | 15 秒 |

### 代价与边界

- 多了一个组件（blackbox-exporter），它自己也是单副本，挂了就没黑盒探测；`up{job="blackbox-todo-api"}` 掉下来说明探测器没了，需要单独告警，目前没配。
- 每 5 秒一次探测，对服务是额外负载；本地演示无所谓，真实环境要评估频率。
- 37 秒仍然不是"秒级"，因为 `for: 30s` 占了 30 秒。再压缩要靠更密的探测和更短的 `for`，误报风险会上升。

证据：`evidence/2026-11-18-1346-drill-redis-down/`
