## 二、两次误判

### 误判一：把“错误消失”归因于重启 Docker Desktop

Docker 在 23:09:40 启动，但 23:15 那次运行仍然报 `unrecognized character in action: U+005C`。错误真正消失是在 23:15:58 脚本改写之后。

验证方法：集群全部正常运行时，用旧写法重跑一次，同样报错；换新写法立刻正常。变量只有 jsonpath 写法，所以原因确定。

### 误判二：把“重建完成”当成“全部检查通过”

脚本最后那句“重建完成”只检查了两个条件：Pod 是否全部就绪、有没有抛异常。而“Service 后端数量”这一项，命令报错后拿到空值，因为没检查退出码，被当成了 0，没有触发任何失败。

事实是：环境确实重建成功了，但对“后端有几个”的报告不可信。报告坏了，比机器坏了更难发现。

## 三、可以复用的四条判断

1. 时间戳优先于回忆。先后顺序靠系统记录，不靠印象。
2. 一次只改一个变量，改完立刻验证。同时改两处，因果关系无法确定。
3. 先看报错文字指向哪一层，再看自己最近动了什么。`U+005C` 指向参数解析，`connection refused` 指向网络或进程，两者不在同一层。
4. 每个关键断言都要有失败分支。数量是 0、结果是空，必须能触发失败，否则检查等于没有。
