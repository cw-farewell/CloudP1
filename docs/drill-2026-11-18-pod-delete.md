# 演练记录：删除一个 API Pod（2026-11-18）

## 目的

验证两件事：

1. `replicas: 2` 加就绪探针的情况下，删掉一个 Pod 用户会不会察觉
2. ReplicaSet 多快能把 Pod 补回来

## 操作

- 注入：`kubectl delete pod <其中一个 API Pod>`
- 观测：集群内起一个探针 Pod（`curlimages/curl`），每秒 `GET /todos`，输出时间戳和状态码
- 时长：注入后观察 45 秒
- 对照：同时用 `kubectl get endpointslice` 观察后端数量

## 结果

| 项目 | 数值 |
|---|---|
| 探针样本数 | 54 |
| 非 200 样本数 | **0** |
| 移除前后端数 | 2（始终没有降到 1） |
| 替换 Pod 创建时间 | 与删除同一秒（09:52:02） |
| 替换 Pod 就绪 | 2 秒内 |
| 当前后端数 | 2 |

**结论：删一个 Pod，用户完全没有感知。**

原因有两层：ReplicaSet 立刻补了一个新 Pod；就绪探针保证新 Pod 就绪之前不会进入 Service 后端，
旧 Pod 在终止过程中也仍然在提供服务。所以后端数量从头到尾没有真正掉到 1。

## 一次差点写错的结论

第一次跑这个演练时，是用 `kubectl port-forward` 到 Service 来发请求的。删掉 Pod 之后，
探针连续返回 `000`，统计出 **39 次失败**，看起来像"用户严重受影响"。

实际是测量方法坏了：`port-forward` 只建立一条 TCP 连接，并且被固定到某个 Pod。
被删的正好是这个 Pod，隧道立即断开，之后所有请求都连不上。服务本身换成另一个 Pod 一直在正常响应。

换成集群内探针（不参与被删对象）之后，结果是 0 次失败。

**同一天、同一次操作、两种测法，结论完全相反。** 差别的唯一来源是观测方式。

这条比演练数字更有价值：判断"用户有没有受影响"之前，先确认"我用来判断的那个东西，
本身会不会被这次故障影响"。如果是，那测出来的不是故障，是观测工具的死因。

## 边界

- 只删了一个 Pod，两个同时删没有测。两个都删才会真正出现"后端为 0"的窗口。
- 新 Pod 的就绪速度依赖镜像已经在本地。如果镜像要重新拉取，补回时间会从 2 秒变成几十秒。
- 集群只有单节点，所以这个演练证明的是"进程级自愈"，不是"节点级容灾"。

## 和另外两场演练的关系

| 演练 | 注入对象 | 用户影响 | 发现耗时 | 恢复 |
|---|---|---|---|---|
| 依赖故障（11-16 / 11-18） | Redis | 3 秒内出现 500 | 211 秒 → 改进后 89 秒 | 6 秒 |
| Pod 删除（本场） | 一个 API Pod | **无** | 不需要告警 | 2 秒内自愈 |

两场对比说明：**这台环境对"单副本组件"敏感，对"多副本组件"有基本容错。**
Redis 是单副本，一停就影响业务；API 是双副本，删一个没有影响。
